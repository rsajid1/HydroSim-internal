# HydroSim Security Plan

Software Security Documentation


This Security Plan defines how the HydroSim team identifies, tests for, and mitigates security risk across the application. HydroSim is a hydroponics simulation platform consisting of a Next.js/TypeScript frontend, a FastAPI/Python backend, AWS Cognito authentication, and a PostgreSQL database hosted on AWS RDS. 

It builds directly on the team's existing HydroSim QA & Testing Strategy document, extending it with an explicit threat model, security-specific testing techniques and tools, authentication/authorization testing, input validation and injection testing, data security checks, and a reporting and remediation process.

Each control described below is checked against the current codebase and marked with a status of Implemented, Partially Implemented, or Planned. This reflects that the plan is a living document, not a claim that every control is already in production. Section 7 consolidates every outstanding item into a single remediation roadmap, targeted for completion before final project delivery.

## 1. Threat Identification

### 1.1 System Overview and Assets

HydroSim simulates plant growth from environmental inputs (pH, EC, temperature, humidity, CO₂) and stores user accounts and simulation state. The assets that require protection are:

- User credentials and identity data, managed through AWS Cognito (signup, login, session tokens).
- Simulation data, including saved plant/shelf states, control settings, and history persisted in PostgreSQL (AWS RDS).
- Simulation outputs, such as the stress and yield predictions generated by `calculatePhysics()`. If manipulated or corrupted, users make real-world planting decisions based on false data.
- Secrets and credentials, including the AWS Cognito client secret, database credentials, and other environment variables used by the backend.
- API surface: the FastAPI endpoints (e.g., authentication routes, `/api/db/health`) that the frontend depends on for correct, trustworthy data.

### 1.2 Identified Threats

The following threats were identified from the project's architecture (AWS Cognito auth, PostgreSQL persistence, a public-facing web frontend, and a Python API) and mapped against the threat categories covered in the Software Security Overview. A code-level review (Section 7) found that the two highest-priority threats below are only partially mitigated today: injection is addressed at the query layer, but the authentication/authorization threat is not, since no route currently verifies a caller's token.

| Threat | Likelihood | Impact | Risk Priority | Testing Focus |
|---|---|---|---|---|
| SQL Injection via API inputs (e.g., signup/login fields, simulation parameters) reaching PostgreSQL | Medium | High | High | Input validation testing, DAST, code review of query construction |
| Broken or weak authentication through AWS Cognito misconfiguration (e.g., missing MFA, weak password policy) | Medium | High | High | Authentication testing, password entropy checks, Cognito config review |
| Exposed secrets/API keys (Cognito client secret, DB credentials) committed to the repo or leaked in logs/error messages | Medium | High | High | Secret scanning, PR review, fail-securely error handling checks |
| Brute-force credential guessing against `/login` (no rate limiting or lockout currently observed) | Medium | High | High | Rate-limit testing, lockout/backoff verification, Cognito throttling config review |
| Cross-Site Scripting (XSS) through unsanitized user input rendered in the UI (e.g., crop names, alert text) | Medium | Medium | Medium | Input validation testing, DAST (OWASP ZAP), output encoding review |
| Broken access control / privilege escalation between user and admin-style roles (if/when RBAC is introduced) | Low-Medium | High | Medium | Authorization testing, RBAC test cases |
| Data corruption from race conditions or invalid writes to simulation state in PostgreSQL | Low | Medium | Medium | Integration testing, DB health checks, transaction review |
| Denial of Service against the API or simulation loop (excessive requests, resource exhaustion) | Low | Medium | Low-Medium | Rate-limiting review, load/availability testing |
| Insecure transmission of data (missing HTTPS/TLS enforcement) between frontend, backend, and RDS | Low | High | Medium | Configuration scanning, TLS verification |

Risk priority is assigned as Likelihood × Impact, consistent with the Risk Assessment approach described in the Software Security Overview. High-priority items (SQL injection, authentication weaknesses, exposed secrets, brute-force login attempts) receive the most testing effort and are gated by the CI pipeline and PR review process before reaching main.

## 2. Testing Techniques and Tools

HydroSim combines automated static analysis, automated dynamic testing, and manual review, matching the layered approach recommended in the course material (Application Security Testing, Web Application Security Testing, Penetration Testing, Configuration Scanning).

### 2.1 Static Application Security Testing (SAST)

| Item | Status |
|---|---|
| ESLint (frontend): runs in CI on every pull request and push to main/dev; enforces code-quality and style rules that catch unsafe patterns before merge. | Implemented |
| Pylint (backend): runs in CI with a minimum score threshold (`--fail-under=7.0`) against `app/` and `config/`, flagging risky code patterns in the FastAPI application. | Implemented |
| Manual code review: every PR requires at least one peer review from a team member other than the author, focused on authentication logic, database queries, and input handling in addition to functional correctness. | Implemented |

### 2.2 Dynamic Application Security Testing (DAST)

| Item | Status |
|---|---|
| OWASP ZAP: scanning the running frontend and backend for common web vulnerabilities (XSS, insecure headers, session issues, injection points) prior to major releases. | Planned |
| Burp Suite (manual/community edition): targeted manual probing of the authentication flow and API endpoints, once route-level authentication is in place. | Planned |
| Manual smoke testing: already required before any PR targeting main (planter UI, simulation loop, alert console, auth flows, DB panel); security-relevant checks are folded into this pass. | Implemented |

### 2.3 Input Validation Checks

Pydantic models (`SignupModel`, `LoginModel`) enforce field-presence validation on the backend today. Format validation (e.g., email format) and password-strength rules are designed but not yet coded (see Section 7).

| Item | Status |
|---|---|
| Field-presence validation on signup and login requests (missing fields rejected). | Implemented |
| Email format and password-strength validation. | Planned |

### 2.4 Tool Summary

| Category | Tool | Purpose | Status |
|---|---|---|---|
| SAST | ESLint | Frontend static analysis / unsafe pattern detection | Implemented |
| SAST | Pylint | Backend static analysis, enforced CI quality gate | Implemented |
| DAST | OWASP ZAP | Automated scanning for XSS, injection, insecure config | Planned |
| DAST | Burp Suite | Manual probing of auth flows and API endpoints | Planned |
| Unit / Integration | Vitest (frontend), pytest (backend) | Security-relevant unit tests | Implemented |
| CI Enforcement | GitHub Actions (HydroSim CI Pipeline) | Runs lint + tests on every PR/push to main and dev | Implemented |
| Secret Detection | PR review / `.gitignore` + CI env stubbing | Prevents `.env` files or hardcoded credentials from being merged | Partially Implemented |

## 3. Authentication and Authorization Testing

### 3.1 Authentication (AWS Cognito)

| Item | Status |
|---|---|
| `get_secret_hash()` computes the Cognito secret hash using HMAC-SHA256; the function exists and is called correctly on signup/login. A dedicated unit test asserting the hash matches a known value has not yet been added. | Partially Implemented |
| Cognito rejects invalid, expired, or tampered tokens for protected routes. No route currently verifies a caller's token at all; this is the highest-priority item in the plan. | Planned (Critical) |
| Failed login attempts return a generic error rather than revealing whether the username or password was incorrect. Currently Cognito's raw error message is forwarded as-is, which can allow username enumeration. | Planned |
| Repeated failed login attempts are throttled or trigger account lockout (Cognito's built-in throttling or an app-layer rate limit). Not yet verified whether Cognito's default throttling is sufficient or whether the app needs its own layer. | Planned |
| Multi-factor authentication (MFA) is available/enforced through Cognito as a defence-in-depth control. Not yet verified against the Cognito pool configuration. | Planned |
| CI stubs Cognito environment variables (region, user pool ID, client ID/secret) so authentication logic can be exercised in automated tests without real credentials. | Implemented |

### 3.2 Password Entropy

Consistent with the entropy formula from the Software Security Overview (Entropy = log2(number of possible combinations)), the target policy is for accepted passwords to fall in the "Strong" range (60+ bits of entropy). This Python-layer check is planned but not yet coded. `SignupModel` currently accepts any non-empty string, and Cognito's own password policy is the only enforcement in effect today.

| Password Example | Approx. Composition | Bits of Entropy (approx.) | Classification | Target Behaviour |
|---|---|---|---|---|
| password123 | 11 lowercase + digits, dictionary word | ~36 | Weak | Reject |
| Hydro2025! | 10 chars, mixed case + digit + symbol | ~59-65 | Weak / borderline Strong | Accept with warning |
| Tr0pica!Grow#42 | 15 chars, full character set | 120+ | Very Strong | Accept |

Cognito itself stores password hashes; HydroSim never stores or logs plaintext passwords.

### 3.3 Access Privileges (Authorization)

HydroSim's design intent is for authenticated users to access only their own simulation data.

| Item | Status |
|---|---|
| A logged-in user can only read/modify their own saved simulation states, not another user's data. Cannot be enforced or verified until route-level authentication is in place. | Planned |
| Unauthenticated requests to protected API routes are rejected rather than defaulting to open access (Fail Securely principle). Currently all API routes accept unauthenticated requests. | Planned (Critical) |
| As role-based features (e.g., admin/reporting views) are introduced, the Principle of Least Privilege will be applied via RBAC test cases before merge. | Planned (Future Work) |

### 3.4 Cross-Origin Resource Sharing (CORS)

The backend configures `CORSMiddleware` (`backend/app/index.py`). The current configuration:

| Setting | Current Value |
|---|---|
| `allow_origins` | Explicit allowlist — `http://localhost:3000`, `http://localhost:3001`, `http://127.0.0.1:3000`, `http://127.0.0.1:3001` (dev only, no production domain configured yet) |
| `allow_credentials` | `True` |
| `allow_methods` | `["*"]` |
| `allow_headers` | `["*"]` |

| Item | Status |
|---|---|
| CORS uses an explicit origin allowlist rather than a wildcard, which is spec-valid alongside `allow_credentials=True`. | Implemented (dev) |
| Production origin added to the allowlist before deployment, with `allow_methods`/`allow_headers` narrowed from `["*"]` to only what the frontend actually needs once a non-localhost origin is present. | Planned |

## 4. Input Validation and Injection Testing

### 4.1 SQL Injection

| Item | Status |
|---|---|
| All database access uses parameterized queries (`cursor.execute(sql, params)`) rather than string concatenation, so user input is always treated as data, never as executable SQL. Confirmed by code review. | Implemented |
| Test cases submitting classic injection payloads (e.g., `"' OR '1'='1"`) to login and data-entry endpoints, asserting the request is rejected rather than causing a server error. | Planned |
| `GET /api/db/health` does not echo raw query text, stack traces, or connection strings on failure. Currently the failure response includes the DB host, database name, and raw driver error text. | Planned |

### 4.2 Cross-Site Scripting (XSS) and Security Headers

| Item | Status |
|---|---|
| User-supplied text rendered in the UI is protected from script execution. No use of `dangerouslySetInnerHTML` was found; Next.js's default JSX escaping is the active defence. | Implemented |
| Cognito tokens (access/ID/refresh) are currently stored in the browser's `localStorage`. This raises the real-world impact of the XSS threat in Section 1: a successful XSS does not just deface the UI, it can exfiltrate tokens and result in full session/account takeover. Migrating to httpOnly, Secure, SameSite cookies for token storage removes this exposure. | Planned |
| Security headers — Content Security Policy (script injection defence-in-depth), `X-Frame-Options`/`frame-ancestors` (clickjacking), and `Strict-Transport-Security` (closes the downgrade/MITM window referenced in Section 5.1). | Planned |

### 4.3 Command Injection and Other Input-Based Attacks

| Item | Status |
|---|---|
| Backend endpoints do not pass user input to shell commands or the file system. Confirmed by code review; no `subprocess`, `os.system`, or `shell=True` calls were found. | Implemented |

### 4.4 Client-Side and Server-Side Validation

Validation is enforced on both layers so that client-side checks improve user experience but are never trusted as the security boundary:

| Layer | Mechanism | Example | Status |
|---|---|---|---|
| Client (frontend) | Form/UI-level checks in React components | `ControlSlider` constrains pH/EC/temperature ranges before submission | Implemented |
| Server (backend) | Pydantic models and route-level checks | Rejects missing fields today; range/format checks planned | Partially Implemented |
| Server (data layer) | Parameterized queries | Simulation and user data reads/writes cannot be altered by crafted input | Implemented |

Test cases target length, format, range, and type for every field identified in the QA & Testing Strategy's unit-test tables (e.g., `calculatePhysics()` inputs, `getGrowthLabel()` boundaries). Server-side range constraints on simulation inputs (`PredictRequest`) are designed but not yet coded.

## 5. Data Security and Privacy Checks

### 5.1 Secure Transmission

| Item | Status |
|---|---|
| All traffic between the frontend, backend, and AWS services (Cognito, RDS) uses HTTPS/TLS. Not yet verified; no `sslmode` parameter is set on the database connection and no HTTPS-redirect middleware exists. | Planned |
| Configuration scanning to confirm TLS is enforced at the load balancer/hosting layer and certificates are valid. | Planned |

### 5.2 Encryption at Rest and in Transit

| Item | Status |
|---|---|
| PostgreSQL data on AWS RDS is encrypted at rest using AWS-managed encryption. No infrastructure-as-code exists in the repo to verify this setting; to be confirmed directly in the AWS console. | Planned |
| Cognito manages password hashing and token issuance; HydroSim never stores or logs plaintext passwords. | Implemented |
| Sensitive configuration values (Cognito client secret, DB credentials) are supplied via environment variables, never committed to the repository. Correctly gitignored and absent from git history; a local `.env` with live credentials was found on disk during review, and the affected credentials have since been rotated. | Partially Implemented |

### 5.3 Data Leakage and Exposure Checks

| Item | Status |
|---|---|
| Error responses return generic messages to the client while detailed information is written only to secure server-side logs. Several endpoints currently return raw exception text directly in the response body. | Planned |
| Debug logging does not print sensitive data. Two debug `print()` statements were found logging full Cognito authentication responses (including access/ID/refresh tokens) to stdout. | Planned |
| The rejected `.env` / hardcoded-credential PR rule is enforced: any PR introducing a committed secret is blocked from merging. | Implemented |
| Periodic manual review of logs and API responses for accidental exposure of personal data beyond what each role is authorized to see. | Planned |

## 6. Reporting and Risk Mitigation Plan

### 6.1 Vulnerability Documentation

Any vulnerability found through SAST, DAST, manual testing, or code review is logged as a GitHub Issue with the following information:

- Description of the vulnerability and how it was found (tool/technique).
- Affected component (frontend, backend, database, CI/CD, or infrastructure).
- Severity rating: Critical, High, Medium, or Low, based on likelihood and impact as in Section 1.
- Proposed fix, or a documented justification if the risk is being accepted rather than fixed.

This process has already been exercised once: this plan was checked against the live codebase in a structured review, producing the findings summarized in Section 7. That review is treated as the first cycle of this reporting process, not a one-off.

### 6.2 Severity Rating Scale

| Severity | Definition | Example |
|---|---|---|
| Critical | Directly exploitable, leads to data breach, full account takeover, or system compromise | No route verifies the caller's token, so every endpoint is currently open |
| High | Significant impact, exploitable with moderate effort | Exception details (DB host, raw error text) returned in API responses |
| Medium | Limited impact or requires specific conditions to exploit | Debug logging of full Cognito token payloads to stdout |
| Low | Minimal impact, defence-in-depth issue, or requires local/insider access | Missing Content Security Policy header |

### 6.3 Fix and Re-Testing Workflow

Remediation follows the same branch-and-PR process already defined in the QA & Testing Strategy's Pull Request Quality Rules, extended with security-specific gates:

- Fixes are made on a `bugfix/` branch and submitted as a PR referencing the originating security issue.
- Automated tests (Vitest, pytest) and CI checks (ESLint, Pylint) must pass before merge, and a new or updated unit/integration test is added to prevent regression of the specific vulnerability.
- At least one peer reviewer confirms the fix addresses the root cause, not just the reported symptom.
- For Critical/High severity issues, a re-test (repeating the original scan or manual probe that found the issue) is performed after merge to confirm closure before the fix is considered resolved.
- The issue is closed only after re-testing confirms the vulnerability no longer reproduces; accepted-risk items remain open/tracked with their justification documented rather than silently closed.

### 6.4 Continuous Monitoring

Because security is addressed throughout the SDLC rather than as a one-time activity, HydroSim treats the CI pipeline (linting and automated tests on every PR/push to main and dev) as the first line of defence. This will be backed by periodic manual DAST scans (Section 2.2) and, as a planned addition, automated dependency-vulnerability scanning (`pip-audit`, `npm audit`) in CI so known vulnerabilities in third-party packages are caught before release.

## 7. Implementation Status Summary & Remediation Roadmap

This plan was checked directly against the current codebase rather than assumed to be accurate. The table below consolidates every outstanding item flagged as not-yet-implemented or unverified elsewhere in this document, with its priority and remediation action. All items are targeted for completion before final project delivery; the Critical item is prioritized ahead of the others.

| Item | Priority | Current Status | Remediation Plan |
|---|---|---|---|
| Route-level authentication (verify Cognito token on protected routes) | Critical | Not Implemented | Add a Cognito JWT verification dependency; apply to all non-auth routes |
| Generic error responses (no leaked exception text) | High | Not Implemented | Replace raw exception text in responses with generic messages; log details server-side only |
| Brute-force / login rate limiting and lockout | High | Not Implemented | Verify Cognito throttling defaults; add app-layer rate limiting on `/login` if insufficient |
| Token storage in `localStorage` (amplifies XSS impact) | Medium-High | Not Implemented | Migrate to httpOnly, Secure, SameSite cookies for Cognito tokens |
| Debug `print()` statements logging Cognito tokens | Medium | Not Implemented | Remove, or replace with `log.debug()` gated on a debug flag |
| Input validation hardening (`SignupModel` password strength, `LoginModel` email format) | Medium | Not Implemented | Add a Pydantic `field_validator` for password rules; change email field to `EmailStr` |
| `/api/db/health` response leaks host/DB name/raw error | Medium | Not Implemented | Strip internal details from the response body |
| Injection-payload regression tests | Medium | Not Implemented | Add automated test cases (SQLi/XSS payloads) to the CI test suite |
| CORS production hardening | Medium | Not Implemented | Add production origin to allowlist; narrow `allow_methods`/`allow_headers` from `["*"]` |
| TLS and RDS encryption enforcement | Medium | Unverified | Add `sslmode='require'` to the DB connection; confirm RDS at-rest encryption in the AWS console |
| MFA enforcement in Cognito | Low-Medium | Unverified | Confirm Cognito user pool configuration |
| Simulation input range validation (`PredictRequest`) | Low-Medium | Not Implemented | Add `Field(ge=..., le=...)` bounds matching frontend slider ranges |
| Security headers (CSP, `X-Frame-Options`, HSTS) | Low | Not Implemented | Add security-headers middleware / Next.js `headers()` config |
